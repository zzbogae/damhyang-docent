# PART 1 — 「씨앗을 바꾼다」가 무슨 말인가

## 1-1. 지금 코드가 하는 일

하빈님 `gems.js`에 이런 함수가 있습니다.

```js
pickGem('2026-W06')  →  'obsidian'
```

주차 이름(`2026-W06`)이라는 **글자를 숫자로 뭉갠 다음, 9로 나눈 나머지**로 광석을 고릅니다.

| | |
|---|---|
| 좋은 점 | 난수가 아닙니다. **같은 주는 언제나 같은 광석** — 앱을 껐다 켜도 안 바뀝니다 |
| 문제 | **그 주에 무슨 일이 있었는지와 아무 상관이 없습니다** |

`2026-W06`이 흑요석인 이유는 그 주에 뭔가 있어서가 아니라 **글자가 그렇게 생겨서**입니다.
주 이름이 `2026-W07`이었으면 다른 광석이 나옵니다.

> **광석이 예쁘긴 한데, 아무것도 말하지 않습니다.**

## 1-2. 바꾸자는 것

글자 대신 **그 주의 판정 결과**를 넣자는 겁니다.

```js
// 지금
pickGem('2026-W06')          // 주 이름

// 바꾸면
pickGem('걸음-많음')          // 그 주에 가장 크게 벗어난 축 + 방향
```

그러면 **걸음이 튄 주는 언제나 호박**이 됩니다. 광석을 보면 어느 기록이 튀었는지 알 수 있습니다.

## 1-3. 그러려면 필요한 것 하나

지금 파이프라인이 내보내는 주간 데이터에 **"어느 축이 가장 크게 벗어났나"**가 없습니다.
`judge.py`가 판정할 때 이미 4축을 다 비교하고 있으니, **그 결과를 한 줄 더 적어 내보내면** 됩니다.

```json
{
  "week": "2026-W06",
  "dominant_axis": "steps",     ← 이 두 줄이 추가
  "direction": "high",
  ...
}
```

**"코드 한 줄"이라고 한 게 이겁니다** — 이미 계산하고 있는 값을 버리지 말고 적어서 넘기는 것.
그러면 앱 쪽은 `pickGem(week.dominant_axis + '-' + week.direction)` 한 줄로 끝납니다.

# PART 2 — 광물 규칙 정본

## 2-1. 네 겹으로 나눕니다

지금 광물 관련 산출물이 여러 사람에게서 나왔는데, **서로 경쟁하는 안이 아니라 서로 다른 겹**입니다.

| 겹 | 언제 보이나 | 무엇이 정하나 | 누가 만들었나 |
|---|---|---|---|
| **① 광석 (겉면)** | 지층 벽에 박혀 있을 때 | **어느 기록이 튀었나** | 하빈 `gems.js` 9종 · 단희 3D |
| **② 균열 (채굴 중)** | 곡괭이 3타 | **아무것도** — 모든 주가 같음 | 하빈 `ore-stage-1·2·3` |
| **③ 코어 단면 (열린 뒤)** | 깨진 다음 | **그 주 7일의 값** | 창 A `core_generator.py` |
| **④ 상태** | 다 캔 뒤 | 이미 봤는가 | 하빈 `state:'mined'` |

**핵심 구분**
> **광석은 "어느 축"을 말하고, 단면은 "그 주가 어땠는지"를 그립니다.**
> 광석은 9종 중 하나로 반복되지만, **단면은 796주가 전부 다릅니다.**

## 2-2. ① 광석 — 9종 배정표

**4축 × 2방향 + 복합 1 = 9.** 하빈님 9종과 개수가 정확히 맞습니다.

| 축 | 방향 | 광석 | 형태 | 색 |
|---|---|---|---|---|
| **걸음** | 많음 | **호박** | 원석 | `#d99a3f` |
| | 적음 | **황철석** | 계단 | `#e8c45f` |
| **잠** | 많음 | **청금석** | 육각주 | `#5a94d6` |
| | 적음 | **월장석** | 판상 | `#cfe0e8` |
| **화면** | 많음 | **자수정** | 군집 | `#a17fd1` |
| | 적음 | **홍옥** | 방추 | `#e88ab5` |
| **기록** | 많음 | **석류석** | 조각 | `#e0705f` |
| | 적음 | **흑요석** | 첨탑 | `#8b87a0` |
| **복합** | — | **형석** | 쌍둥이 | `#6fc79a` |

**색 계열이 축을 따라갑니다** — 노랑=걸음, 청=잠, 보라~분홍=화면, 초록=복합.

### 기록 축만 예외입니다 (일부러)

흑요석(회흑)과 석류석(붉은색)은 같은 계열이 아닙니다. **그런데 이게 낫습니다.**

> 기록이 **적은** 주 = 흑요석. 검고, 안이 비어 있습니다. 아무것도 안 쓴 주니까요.
> 기록이 **많은** 주 = 석류석. 붉고, 알갱이가 빽빽합니다.

색 계열을 맞추는 것보다 **쓴 주와 안 쓴 주의 대비**가 더 잘 읽힙니다. 예외로 두고 이유를 적어둡니다.

### 복합(형석)이 제일 중요합니다

두 축 이상이 동시에 벗어난 주 = **교차검증된 주**입니다.
우리 최대 차별점인데 지금까지 **그림으로 보여줄 방법이 없었습니다.**
형석은 9종 중 유일한 초록이라, 지층 벽에서 딱 눈에 띕니다.

## 2-3. 산출 규칙 (개발용 · 난수 없음)

```
입력: 그 주의 4축 편차 z_걸음 z_잠 z_화면 z_기록

1) |z| ≥ τ 인 축의 개수를 센다
     2개 이상 → 형석 (복합)
     1개      → 그 축 + 부호로 위 표에서 선택
     0개      → 코어를 만들지 않는다 (지층에 그냥 남음)

2) 동점이면 → 교차검증 채널 수가 많은 축
   그래도 같으면 → 걸음 → 잠 → 화면 → 기록 순서 고정
```

**같은 데이터를 넣으면 언제나 같은 광석이 나옵니다.**

> ⚠ **τ(임계값)를 정해야 합니다.** 너무 낮으면 전부 형석이 되고, 너무 높으면 형석이 안 나옵니다.
> 데모 80주로 돌려서 분포를 보고 정하는 게 맞습니다.

## 2-4. ② 균열 — 데이터와 무관

| 단계 | 에셋 |
|---|---|
| 1타 | `ore-stage-1-intact` |
| 2타 | `ore-stage-2-crack` |
| 3타 | `ore-stage-3-shatter` |

**모든 주가 똑같습니다.** 여기에 의미를 넣지 않습니다 — 채굴은 사용자의 행동이지 데이터가 아닙니다.
`mine-interactions.js`의 `initMineableCore`가 3타·소리·파티클을 다 처리합니다.

## 2-5. ③ 코어 단면 — 여기만 매주 다릅니다

**⚠ 단희님 3D의 패턴 A·B·C를 그대로 쓰면 안 됩니다.**
지금 실제 광물 사진 텍스처로 보이는데, 그러면 **796주가 전부 같은 무늬**가 됩니다.
"AI가 만든 게 아니라 당신의 기록으로 계산된 무늬"가 그 자리에서 무너집니다.

**대신 이렇게 나눕니다.**

| | 무엇 | 누가 |
|---|---|---|
| 겉테두리 | 단희 3D — Stone Concept A/B, 깨진 상태 | 그대로 사용 |
| **안쪽 결** | **코드가 그림** — 그 주 7일의 일별 값 | `core_generator.py` |
| 무늬 성격 | 단희 패턴 A/B/C를 **텍스처가 아니라 기준**으로 | 규칙으로 전환 |

**패턴 A·B·C의 새 역할**

| | 성격 | 언제 나오나 |
|---|---|---|
| A | 결이 굵고 경계가 뚜렷 | 하루하루 편차가 큰 주 |
| B | 층이 규칙적 | 매일 비슷한 주 |
| C | 여러 색이 섞임 | **복합(형석) — 여러 축이 동시에 튄 주** |

> 세 안을 버리는 게 아닙니다. **텍스처에서 규칙으로 옮기는 것**입니다.

# PART 3 — 앱의 목적

## 3-1. 말씀하신 게 층이 하나 더 있는 겁니다

지금까지 정한 한 문장은 **무슨 일이 일어나는가**만 말합니다.
말씀하신 건 **그래서 무엇이 달라지는가**입니다. 둘 다 필요하고, 순서가 있습니다.

| 층 | 문장 | 쓰는 곳 |
|---|---|---|
| **① 무엇이 일어나나** | "정확한 걸 찾으러 간 게 아닌데, **그 시기가 어떤 느낌이었는지가 통째로 돌아옵니다.**" | 발표 첫 30초 · 원페이지 |
| **② 그래서 무엇이 달라지나** | "그리고 그 느낌이 **내일 하루를 아주 조금 다르게** 만듭니다." | ① 바로 뒤 |
| **③ 어떻게 그렇게 되나** | 앱이 묻지 않습니다. **묻고 싶어지게 둡니다.** | 기획서 · 심사 질문 대비 |

## 3-2. ⚠ 여기서 선을 하나 그어야 합니다

말씀 중에 이런 대목이 있었습니다 — *"질문을 던져 내일을 어떻게 살고 싶은지"*.

**그 질문을 앱이 던지면 안 됩니다.**

| | 왜 |
|---|---|
| "내일을 어떻게 살고 싶으세요?" | **먼저 말 걸기.** 원칙 위반 |
| "더 나은 하루" | **앱이 「낫다」를 정의**하는 것. 판정 |
| 매일 질문이 뜨는 구조 | 셀프리치가 하는 것. 우리가 대조로 세운 것 |

**그런데 이미 답이 설계에 있습니다 — 편지입니다.**

> 앱은 날짜와 사실 한 줄까지만 인쇄합니다.
> `2026년 9월 6일 · 이 주는 새벽에 남긴 글이 평소보다 많았습니다.`
> **그 아래는 빈칸입니다. 질문은 사용자가 자기에게 던집니다.**

> 민디 — "무엇을 쓰실지는 제가 모릅니다. 종이만 놓아두겠습니다."

**질문의 주체가 앱이면 잔소리고, 사용자면 성찰입니다.** 우리는 후자만 합니다.

## 3-3. 그래서 「내일이 조금 달라진다」는 어디서 오나

세 장치가 이미 다 있습니다.

| 장치 | 하는 일 |
|---|---|
| **지금의 나** | 이번 주와 가장 닮았던 과거를 보여줌 → *"그때 나는 어떻게 했더라"*가 저절로 생김 |
| **원문 카드** | 그때 쓴 문장을 그대로 → 요약하면 남의 말이 됩니다. 원문이라 내 말입니다 |
| **편지** | 그 자리에서 미래의 나에게 남김 → 다음 주·다음 달에 되돌아옴 |

**과거 → 지금 → 내일이 한 화면에서 이어집니다.** 앱이 한 마디도 안 하고요.

## 3-4. 「느낌을 간직한다」

말씀하신 마지막 부분이 **아웃풋 문제의 답**이기도 합니다. 8/19에 지목하신 구멍이요.

| 무엇을 가져가나 | |
|---|---|
| 코어 카드 내보내기 | 그 시기가 손에 남음 |
| 화분 · 새싹 | 다녀간 자리가 공간에 남음 |
| 편지 | **느낌이 시간에 남음** — 다음 주의 내가 받음 |

> 셋 중 **편지가 유일하게 미래로 갑니다.** 나머지 둘은 저장이고, 편지만 배달입니다.

## 3-5. 발표에서 쓸 두 문장

> "정확한 걸 찾으러 간 게 아닌데, 그 시기가 어떤 느낌이었는지가 통째로 돌아옵니다.
> 그리고 그 느낌이 내일 하루를 아주 조금 다르게 만듭니다."

**"조금"과 "다르게"를 빼지 마세요.**
「많이」가 되면 못 지킬 약속이 되고, 「낫게」가 되면 판정이 됩니다.
