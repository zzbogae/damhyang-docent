# 사진 안전 필터 시험 결과 (2026-09-11)

사진 필터(`web/src/filter/photoFilter.ts`)를 실제 Chromium 에서 시험셋 39장에 돌린 결과입니다. 필터는 기기 안(브라우저)에서만 실행되고, 사진을 서버로 보내지 않습니다.

- 실행: `cd web && npm run assets && npx playwright test -c playwright.lab.config.ts`
- 시험 페이지: `web/lab/filter.html` (`?prod` 를 붙이면 앱 기본값으로 검사)
- 결과 원본: `web/lab/filter_report.json`, 화면: `web/lab/filter_grid.jpg`(앱 기본값), `web/lab/filter_grid_lab.jpg`(모든 후보 점수 기록용)
- 환경: Apple M4, Playwright Chromium(headless), WebAssembly CPU 단일 스레드

## 1. 결론

앱 기본값에서 숨겨야 할 사진 24장을 모두 숨겼습니다(재현율 100%). 숨긴 28장 중 4장은 보여도 되는 사진이었습니다(정밀도 85.7%). 계획서의 목표(재현율 98% 이상, 정밀도는 양보)를 이 시험셋에서는 맞췄습니다. 다만 기준값을 같은 39장으로 정했기 때문에, 팀원이 동의한 실제 사진 500장으로 다시 재야 합니다(계획서 1-6).

| 항목 | 값 |
|---|---|
| 재현율(숨겨야 할 사진 중 숨긴 비율) | 24/24 = 100% |
| 정밀도(숨긴 사진 중 숨겨야 했던 비율) | 24/28 = 85.7% |
| 잘못 숨긴 사진 | 비빔밥(얼굴 점수 0.58), 도시 야경(0.52), 개·고양이(동물 얼굴 0.74), EXIF 없는 PNG 풍경(화면 캡처 규칙) |
| 모델 준비(첫 사진 전 1회) | 0.6~1.9초 |
| 장당 처리 시간 | 중앙값 170~270ms, 상위 10% 약 450~500ms |
| 화면 캡처 규칙으로 걸린 사진 | 장당 1~15ms(해독하지 않음) |

시간은 같은 맥에서 다른 빌드·테스트가 함께 돌 때 측정해서 폭이 있습니다. 한 주(사진 30장 안팎)를 처음 열 때 5~8초가 걸리는 수준이고, 결과는 저장해 두므로 두 번째부터는 기다리지 않습니다.

실제 개인 기록은 쓰지 않았습니다. 정답은 `web/lab/testset/labels.json` 에 있습니다.

| 구분 | 장수 | 출처 |

| 글자·문서(숨겨야 함) | 9 | AI 생성 문서·영수증·화이트보드·노트북 화면·손글씨 노트, PIL 로 그린 문서·영수증·가짜 회원증, JPEG 로 저장한 대화 화면 |

어려운 경우 5장은 15m 거리 가족 소풍(얼굴 폭이 사진의 2~3%), 공연장 관객, 옆얼굴, 픽셀째 90도 돌아간 사진, 요가 자세의 작은 옆얼굴입니다. AI 이미지는 `web/lab/tools/gen_ai_images.py`(OpenRouter `google/gemini-3.1-flash-image-preview`)로 만들었고, 시험셋 조립은 `web/lab/tools/build_testset.py` 입니다.

## 3. 검사 순서와 기준값

| 순서 | 검사 | 기준값 | 근거 |
|---|---|---|---|
| 1 | 화면 캡처: 카메라 제조사·모델 EXIF 가 없고 PNG 이거나 파일명이 스크린샷 | 규칙 | 해독 전에 끝나서 가장 빠름 |
| 2 | 글자 영역: PP-OCRv5 mobile det 확률맵에서 0.3 넘는 픽셀의 비율 | 1.5% 이상이면 숨김 | 문서류 2.7~12.0%, 문서가 아닌 사진 1% 미만 |
| 3 | 얼굴(사진 전체): BlazeFace 가까운 거리용 + 먼 거리용 | 점수 0.5 이상 | 실제 얼굴 대부분 0.59~0.95(공연장 관객 0.46~0.52) |
| 4 | 작은 얼굴(3×3 타일, 25% 겹침, 먼 거리용 모델): 앞 단계에서 숨길 이유가 없을 때만 | 점수 0.6 이상 | 작은 얼굴 사진의 최고 점수 0.76~0.84, 얼굴 없는 사진 0.53 이하 |

모델을 불러오지 못하거나 사진을 해독하지 못하면 `status: 'error'` 를 돌려주고, 앱은 그 사진을 보여 주지 않습니다(닫힌 쪽으로 실패).

## 4. 기준값을 정한 과정

처음에는 글자 3%, 얼굴 0.5, 타일 검사 없이 돌렸고 재현율이 22/24(91.7%)였습니다. 놓친 두 장은 15m 거리 가족 소풍과 공연장 관객으로, 얼굴이 사진 폭의 1.5~3% 였습니다. BlazeFace 는 사진 전체를 192px 로 줄여 넣기 때문에 이런 얼굴은 몇 픽셀로 줄어듭니다.

그래서 사진을 3×3 타일로 나눠 먼 거리용 모델을 한 번 더 돌리는 단계를 넣었습니다. 타일에서 나온 최고 점수는 작은 얼굴 사진이 0.76~0.84, 얼굴 없는 사진이 0.53 이하여서 타일 기준을 0.6 으로 두었고, 재현율이 24/24 가 되었습니다. 타일 원본 해상도는 1600px 과 960px 의 결과가 같아서 해독이 가벼운 960px 로 정했습니다.

글자 기준은 3% 에서도 누락이 없었지만, 영수증(4.7%)과의 거리가 가까워 1.5% 로 낮췄습니다. 문서가 아닌 사진 중 가장 높은 값이 1% 미만이라 오탐은 늘지 않았습니다.

얼굴 기준을 0.6 으로 올리면 이 시험셋에서는 정밀도가 92.3% 로 오르고 재현율도 그대로입니다. 하지만 요가 사진의 옆얼굴(사진 전체 점수 0.59~0.60)이 타일 검사에만 기대게 되어 여유가 없으므로, 누락을 더 피하는 쪽인 0.5 를 기본값으로 두었습니다. 기준값별 결과 전체는 `filter_report.json` 의 `sweep` 에 있습니다.

## 5. 알려진 한계

- 본인 얼굴과 타인 얼굴을 구분하지 않습니다. 구분하려면 얼굴 인식(생체정보 처리)이 필요해서 모든 얼굴을 같은 규칙으로 숨깁니다.
- 흐린 썸네일은 검출된 얼굴만 모자이크합니다. 공연장처럼 얼굴이 아주 작고 많은 사진은 검출되지 않은 얼굴이 썸네일에 남을 수 있습니다. 이런 사진도 기본으로 숨겨지므로, "사람이 찍힌 사진 보기"를 누른 경우에만 보입니다.
- 동물 얼굴을 사람 얼굴로 잡는 오탐이 있습니다(개·고양이 사진).
- 메신저로 받은 사진처럼 EXIF 가 없는 PNG 는 화면 캡처 규칙에 걸려 숨겨집니다. 규칙상 의도한 오탐입니다.
- 픽셀째 돌아간 사진(EXIF 방향 정보 없음)은 가까운 거리용 모델이 0.80 으로 잡았지만, 다른 각도에서는 놓칠 수 있습니다. EXIF 방향이 있는 사진은 브라우저가 바로 세운 뒤 검사합니다.
- 크롬·엣지는 HEIC 를 직접 풀지 못해 libheif-js(2.0MB, 처음 HEIC 를 만날 때만 불러옴)로 풉니다. 사파리는 기본 해독을 씁니다.
- 기준값을 시험셋 39장으로 정했으므로 과적합 가능성이 있습니다. 팀원 사진 500장 라벨로 다시 재야 합니다.

## 7. 메모 필터와 원문 고르기

- 메모 필터(`web/src/filter/memoFilter.ts`): 비밀번호·카드번호(룬 검사)·계좌번호·주민번호·전화·이메일·API 키·개인 키·JWT·URL 속 토큰·무작위 문자열(엔트로피)을 찾으면 `secret`, 위기 표현 사전에 걸리면 `crisis` 입니다. 단위 테스트 43개(`web/tests/memoFilter.test.ts`, 예시는 모두 지어낸 값)가 통과합니다. "죽고 싶을 만큼 맛있다" 같은 과장 표현도 위기 표현으로 잡는데, 누락보다 오탐이 낫다는 원칙에 따라 그대로 두었습니다. 위기 표현이 걸린 원문을 열기 전에 보여 줄 도움 안내 문구는 `CRISIS_HELP`(자살예방상담전화 109)입니다.
- 원문 고르기(`web/src/relic/select.ts`): `secret` 메모는 절대 고르지 않고, `crisis` 메모는 고르되 `gated_memo_ids` 로 표시합니다. 배지에 따라 새벽 메모·긴 메모·새벽 사진을 먼저 고르고, 같은 날·같은 시각에 몰린 글은 나눠 고르며, 글자 3-gram 자카드 0.6 이상인 글은 하나만 남깁니다. 사진은 필터 결과가 `ok` 인 것만 고르고, 필터를 아직 거치지 않은 사진은 `pending_photo_ids` 로 돌려줍니다. 단위 테스트 10개(`web/tests/relicSelect.test.ts`)가 통과합니다.

## 8. 비슷한 사진 묶기

여행 주처럼 거의 같은 사진이 여러 장이면 주 상세에 한 장만 보여 주고 "비슷한 사진 N장" 버튼으로 펼칩니다(`web/src/photos/similar.ts`). 필터를 통과한 미리보기(긴 변 320px)를 9×8 로 줄여 차이 해시(dHash, 64비트)와 평균 색을 만들고, 찍은 시각 순서로 앞 묶음과 견줍니다.

- 같은 날 60분 안에 찍었으면 해밍 거리 14 이하, 시각이 멀면 4 이하(사실상 같은 사진, 저장 경로가 다른 복사본 등)일 때 묶습니다.
- 평균 색의 채널 차이가 28 을 넘으면 묶지 않습니다. 하늘·벽처럼 무늬가 거의 없는 사진은 차이 해시가 서로 비슷해지기 때문입니다.
- 해시를 만들지 못한 사진은 묶지 않고 그대로 보여 줍니다. 가려진 사진(얼굴·글자·화면 캡처)은 묶기 대상이 아닙니다.

시험(`npx playwright test -c playwright.lab.config.ts similar`, Chromium, 시험셋 37장): 사진마다 흔한 변형을 만들어 원본과 묶이는 비율을 재고, 서로 다른 사진 666쌍이 잘못 묶이는지 봤습니다. 결과 전체는 `web/lab/similar_report.json` 입니다.

| 변형 | 묶인 비율(기준 14) |
|---|---|
| 재압축(JPEG 품질 0.4) | 100% |
| 밝기 +15% | 100% |
| 옆으로 5% 옮김 | 100% |
| 연속 촬영(밝기 +5%, 3% 옮김) | 92% |
| 3도 기울임 | 73% |
| 가장자리 6%씩 잘라 확대 | 70% |

서로 다른 사진 666쌍 가운데 기준 14 에서 묶인 쌍은 7개입니다. 2개는 시험셋 안에 실제로 같은 사진이 들어 있던 쌍(카카오톡으로 받은 풍경, EXIF 방향만 다른 셀카)이고, 5개는 화면 캡처·문서 사진끼리의 쌍이라 필터에서 이미 가려져 묶기 대상이 되지 않습니다. 보여 주는 사진끼리 잘못 묶인 쌍은 없었습니다. 기준을 10 으로 낮추면 변형 재현율 평균이 89% 에서 74% 로 떨어지고 잘못 묶이는 쌍은 줄지 않아서 14 를 기본값으로 두었습니다.

한계: 시험셋이 37장이고 한 장면을 실제로 여러 번 찍은 사진이 없어서 변형으로 대신했습니다. 팀원 사진 500장 라벨을 만들 때 "같은 장면 묶음" 라벨도 함께 달면 기준을 다시 잴 수 있습니다.
